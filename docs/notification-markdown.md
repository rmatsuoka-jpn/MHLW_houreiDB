# 通知の取得とMarkdown変換

## 通知IDの見つけ方

1. [通知の目次（体系）検索](https://www.mhlw.go.jp/hourei/html/tsuchi/contents.html)は、目次と検索結果を別々のフレームで表示する。[目次フレーム](https://www.mhlw.go.jp/web/t_tenkai?type=1)のHTMLには、各階層を開くための `t_tenkai` リンクが含まれる。展開状態を表す `stat` と対象階層の `tkNo` を含むため、取得したHTMLのリンクをそのまま使う。
2. 末端の項目には、分類別の一覧を表示する `t_taikeisrch` リンクがある。[老人福祉法の分類](https://www.mhlw.go.jp/web/t_taikeisrch?type=1&taikeicode=100101&sort=0&page=0)では `page=0` が先頭一覧、`page=1` が次の一覧。分類コードと並び順を維持し、分類ごとの表示件数と取得結果を照合する。
3. 一覧には `t_doc` のリンクがあり、`dataId` が通知ID。本文ページの番号は一覧と異なり、`pageNo=1` から始まる。複数分類に出る通知は、一覧の分類情報を保持したうえで、本文の取得時に通知IDで重複をまとめる。

2026年11月26日の確認では「第10編 老健 → 第1章 老健 → 老人福祉法」は192件と表示され、最初の2ページで1〜20件目と21〜40件目が取得できた。件数はサイトの更新で変わるため、固定値として使わない。全分類の巡回と件数照合は今後の作業。

## Markdownの変換ルール

| 対象 | 初版の処理 |
| --- | --- |
| ファイル | 1通知1ファイル。ファイル名は `通知ID.md`、文字コードはUTF-8。全ページの取得・変換が完了してから出力する。 |
| 出典 | 件名、通知ID、原本URL、取得日、Markdownへの加工表記を記録する。原本から抽出できる発出日と通知番号を記録する。 |
| 本文 | 各ページの `#contents` を原文の順序でつなぎ、ページごとに原本リンクを付ける。HTMLで明示された見出しをMarkdownに変換する。字下げだけで示された階層は原文の項番と文章を残す。 |
| 表 | セル結合を残すため、Markdown内にHTMLの表として保持する。登録先のRAGがHTMLの表をどう取り込むかは実際のデータで確認する。 |
| 本文中の画像 | 出現位置に「原本に画像あり」と記録する。画像名や代替テキストがあれば添え、画像または原本の該当ページにリンクする。画面操作用のアイコンを除く。 |
| 添付一覧の画像 | 通知末尾に画像名、画像リンク、確認できた原本ページを記録する。画面上で同じ添付一覧が複数箇所に表示されるため、同一画像URLは1件にまとめる。 |

画像ファイルの保存やOCRは初版の対象外。画像内にだけ記載された数値、条件、様式の項目は原本で確認する。利用上重要なものは原本と照合した転記の追加を検討する。

厚労省DBの掲載本文に省略表記がある場合は、そのまま残す。例えば [厚生省職員表彰規程の実施について](https://www.mhlw.go.jp/web/t_doc?dataId=00ta0019&dataType=1&pageNo=1) には「別添1〔略〕」と「〔以下略〕」がある。掲載ページをすべて取得できても、省略された別添まで揃うわけではない。

`--save-source` のJSONには、通知ID、取得日、各ページのHTMLが原本の順序で入る。このファイルを `--source` で渡すと、元の取得日を維持して再生成できる。再現には同じコードのコミットと依存関係を使う。

## 一分野から取得範囲を広げる

以下は一括取得を実装する際の設計。最初は一分野の数十件で、件数照合と本文・表・別添の変換品質を確認する。

1. **通知の一覧台帳を作る。** 末端分類の全ページを巡回し、通知ID、件名、発出日、通知番号、分類、本文URLを記録する。複数分類に載った通知は分類との対応を残し、本文は通知ID単位で取得する。分類単位で画面の表示件数と取得した行数を照合してから、分類を横断した重複を集計する。
2. **取得と変換を分ける。** HTMLは公開リンクから直接取得する。ブラウザー操作が必要な箇所が見つかった場合は、その箇所に限ってPlaywrightなどを検討する。PDFは文字抽出を試し、画像やスキャンPDFは検索の必要性に応じてOCRする。別紙や様式は元の通知とひも付け、原本と変換結果を照合できるようにする。
3. **取りこぼしと更新を追う。** 分類・ページ・通知IDごとに取得結果と失敗理由を記録し、失敗箇所から再開できるようにする。同じ通知IDの本文や添付の更新を検知する。新着通知PDFとDB掲載分は、通知番号・発出日などで照合し、対応が不明な段階で統合しない。
4. **適用時点を確認できるようにする。** 改正・廃止・適用日の根拠と確認時点を記録する。適用状況が不明な通知を自動で現行扱いせず、RAGが旧版を現在の取扱いとして答えないようにする。

対象範囲の初期目標は、厚労省DBの掲載分。厚労省は所管の通知等をすべて収録しているわけではないと明記している。事務連絡などを含める場合は分野別の掲載元も確認する。[利用に際しての注意事項](https://www.mhlw.go.jp/hourei/readme.html)

DBは毎月更新される。最新分が必要な場合は登載準備中の新着通知も取り込み、定期更新一覧で新規・改正・廃止を照合する。[登載準備中の新着通知](https://www.mhlw.go.jp/hourei/new/tsuchi/newindex.html) · [定期更新一覧](https://www.mhlw.go.jp/hourei/new/update/data.html)

調査では本DB専用の公開APIや一括ダウンロードの案内は確認できていない。多数の通知を取得する前に、利用条件と robots.txt、取得対象のアクセス制限を確認し、リクエストは直列に間隔を空ける。出典と加工した旨はMarkdownにも残す。[厚生労働省の利用規約](https://www.mhlw.go.jp/chosakuken/) · [robots.txt](https://www.mhlw.go.jp/robots.txt)
