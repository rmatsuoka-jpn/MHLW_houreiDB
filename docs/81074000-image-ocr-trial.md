# タール色素の省令で画像OCRを試す

対象は厚生労働省法令等データベースサービスに掲載された、全8ページ・添付画像25点の省令。本文での使われ方が異なる図版4点を取得し、Tesseract 5.5.0の英語モデルで処理した。原本画像を目視で照合した内容を `docs/examples/` にまとめた。[省令の原本](https://www.mhlw.go.jp/web/t_doc?dataId=81074000&dataType=0&pageNo=1)

## 原文と照合したMarkdownの表示例

本文6ページでは、屈折率と比重の記号だけが画像になっている。値は本文HTMLにあるため、記号と値の関係が分かるように整形できる。[6ページの原本](https://www.mhlw.go.jp/web/t_doc?dataId=81074000&dataType=0&pageNo=6)

| 項目 | 記号 | 本文に掲載された範囲 |
| --- | --- | --- |
| イソプロピルエーテルの屈折率 | $n_{\mathrm{D}}^{20}$ | 1.368以上1.369以下 |
| イソプロピルエーテルの比重 | $d_{4}^{20}$ | 0.723以上0.725以下 |

表は画像と本文を照合して作成した表示例。現在の `--ocr-dir` では、元の画像リンクを本文に残し、照合済みMarkdownを該当ページ末尾に追記する。本文中の記号と値を一行で保持するには、画像リンクの位置に記号を挿入する処理が必要になる。スペクトルの個々の波数と強度は原本の図を参照する。本文の化学式に使われているHTMLの下付きは、現行の変換では通常の文字として出力される。

## 再現手順

```sh
python notice_to_md.py 81074000 --data-type 0 --save-source source/81074000.json
python notice_images.py source/81074000.json --out output/ocr-input/81074000
python notice_to_md.py 81074000 --source source/81074000.json --ocr-dir docs/examples --out output/with-ocr
```

Tesseractの設定はスペクトル図と比色管の全体画像が `-l eng --psm 11`、記号2点と比色管の寸法部分が `-l eng --psm 7`。記号の拡大には8倍のLanczosリサンプリングを使った。比色管の縦方向の寸法は原寸で左上 `(171, 79)`、右下 `(187, 135)` の範囲を切り出し、時計回りに90度回転して6倍に拡大した。

この試行では原本JPEG4点でOCRを実行し、本文1・6・7ページの該当HTMLを使った入力で、それぞれの照合済みMarkdownが一度ずつ追記されることを確認した。省令全8ページの一括変換は未確認。

## Windows標準OCRでの追加検証

NDLOCR-Liteの公式Windows版はダウンロードが完了せず、この環境のPythonからもPyPI版を取得できなかったため、代替としてWindows標準OCR（`Windows.Media.Ocr`、日本語モデル `ja`）で原本4点と加工画像を比較した。ChatGPTでも原本4点を再確認した。この会話には前回の正解画像と照合結果が含まれるため、ChatGPTの読み取りは独立した精度比較には含めていない。Mathpix Snipは試用画面でログインが必要だった。

| 画像 | 原寸の結果 | 加工後の結果 |
| --- | --- | --- |
| 7912985・スペクトル図 | 「赤色102号」「透過率」「波数」を認識。縦軸の `36.0` に相当する箇所は `3 8 』` となり、単位 `cm⁻¹` も `c m-l` になった。 | `36.0` の目盛りだけを切り出すと `36 . 0`。空白を除くと原本と一致した。 |

## GPTのブラインド比較

会話の履歴を引き継がないGPTサブエージェント2つを使った。片方には原寸JPEG4点、もう片方には加工画像5点だけを渡した。ファイル名を記号に置き換え、原本のURL、本文、正解、OCR出力を伏せた。各条件の読み取りは1回。

| 画像 | 原寸JPEGを読んだ結果 | 加工画像を読んだ結果 |
| --- | --- | --- |
| 7912985・スペクトル図 | 「赤色102号」、縦軸「透過率（%）」、横軸「波数（cm⁻¹）」を認識。両軸の数値目盛り14個は原本と一致。 | `36.0` の切り出しは `36.0`。 |
| 7913007・屈折率 | 最有力は `n_{D}^{20}`。右上の `20` は明瞭と回答し、左の `n` と右下の `D` は不確かとした。 | `n^{20}_{\mathrm{D}}`。左の `n` と右下の `D` はやや不鮮明とした。 |
| 7913008・比重 | 最有力は `d_{4}^{20}`。左の `d` は不確かとした。 | `d^{20}_{4}` と回答し、留保は付かなかった。 |
| 7913009・比色管 | 横寸法 `20～22 mm`、縦寸法 `35～45 mm`、容量目盛り `50 mL` の対応を読み取った。 | 縦寸法の切り出しは `35〜45`。容量付近の切り出しは上段 `mL`、下段 `50`、その右に横線と回答。 |

スペクトル図の原寸画像で得た数値は、縦軸が `110.0, 90.0, 72.0, 54.0, 36.0, 18.0, 0.0`、横軸が `4000.0, 3400.0, 2700.0, 2000.0, 1400.0, 1000.0, 600.0`。波形から数値を推定するようには指示していない。

加工画像は、Windows標準OCRの追加検証で使った `36.0` の切り出し、記号2点のLanczos 8倍拡大と白余白、比色管の縦寸法と容量欄の切り出しを使用した。記号2点とも最有力の読みは照合済みのLaTeXと一致した。屈折率の記号は加工後も字形に不確かさが残った。画像4点・各条件1回の試行結果。

## Pix2Textのローカル比較

Pix2Textの公開数式認識モデル MFR 1.5 を使い、WindowsのCPUで原寸JPEGと8倍拡大・白余白付きの画像を比較した。公式のモデルファイル2点のSHA-256を照合した。推論はPythonパッケージの高水準APIを介さず、ONNX Runtime 1.20.1 のCPUプロバイダーで実行した。公開設定どおりにRGB・384 × 384のバイキュービック補間、画素値の正規化を行い、各ステップで最大スコアのトークンを選び、公式語彙のByteLevel方式で復号した。4条件とも終了トークンを受け取った。画像の認識処理は端末上で行った。[公式モデルと設定](https://huggingface.co/breezedeus/pix2text-mfr-1.5/tree/6e5376e5bb0b152d5796506cc0f150f1aaef3222)

| 記号 | 条件 | モデルの生出力 | 原本との照合 |
| --- | --- | --- | --- |
| 屈折率 $n_{\mathrm{D}}^{20}$ | 原寸 | `\operatorname { n o } ^ { 2 0 }` | 上付きの20は一致。下付きのDがなく、文字列「no」を演算子として出力した。 |
| 屈折率 $n_{\mathrm{D}}^{20}$ | 8倍拡大＋白余白 | `\mathrm { n } _ { 0 } ^ { 2 0 }` | 基底のnと上付きの20は一致。下付きのDを数字の0と誤読した。 |
| 比重 $d_{4}^{20}$ | 原寸 | `\mathbf { d } _ { 4 } ^ { 2 0 }` | d、下付きの4、上付きの20が一致。dは太字で出力された。 |
| 比重 $d_{4}^{20}$ | 8倍拡大＋白余白 | `\mathrm { d ^ { 2 0 } }` | dと上付きの20は一致。下付きの4が欠落した。 |

基底文字・上付き・下付きのすべてが一致したのは、比重の原寸画像の1条件だった。拡大の効果は記号によって異なった。GPTの前回試行では記号2点とも最有力候補が原本と一致したが、屈折率では字形に不確かさが残った。

## Pix2Textの10画像比較

厚労省の原本2点と、正解がわかるように作成した数式画像8点の合計10点を用意した。以前の試行で使った総和・極限・不等号の3式は今回の画像セット用に描き直した。各画像を原寸と8倍拡大・白余白付きで1回ずつ、計20条件で比較した。8倍拡大にはグレースケール化とLanczos補間を使い、四辺に24ピクセルの白余白を加えた。モデル・CPU・正規化は前節と同じ。長い式に対応するため出力上限を128トークンにした。生出力と終了トークンの有無は[結果JSON](examples/pix2text/results.json)に収録した。
